# IssueFlow

针对企业员工通过聊天工具反馈问题时存在信息分散、人工分类效率低、处理进度不透明及操作难以追溯等问题，设计**企业内部智能工单管理系统 IssueFlow **，实现反馈信息统一登记、智能分类与全过程状态追踪。



采用 **FastAPI + Next.js + PostgreSQL** 构建，支持规则匹配与 LLM 实现混合智能分类，并通过异常降级与人工复核保证分类可靠性，保存操作历史与工单状态实现进度跟踪与溯源，结合JWT、RBAC、数据库唯一约束、事务与乐观锁，保证用户数据隔离、重复提交幂等性以及并发操作一致性。



## 系统边界与职责划分

### 系统功能边界

该系统为V1版本，只满足基本功能，打通核心业务链路，不引入过多复杂状态。定位为简单工单管理系统，主要实现工单提交、智能分类、查询、状态跟踪及操作记录。暂不考虑以下内容：
1、暂不支持工单撤销、删除等操作，因为其会引入过多状态

2、暂不支持接单和任务分配，采用所有技术操作员共享工单池，为了简化操作

3、暂不支持工单具体解决方法，因为其需具体业务具体讨论

3、暂不支持评论、聊天、消息通知等，因该不属于核心业务

4、暂不支持微服务、Redis、消息队列，因该服务暂时体量较小

上述内容作为V1版本暂时不考虑，后续可以考虑逐步引入，完善项目



### 系统使用者与权限边界

系统包含普通员工和技术支持人员两类用户，未来可以拓展为系统管理员

普通员工可以提交工单、查看提交工单及其处理历史

技术支持人员可以查看全部工单、人工修正分类、更新工单

具体的权限如下：

| 提交工单           | ✅                | ✅                   |
| 查看自己提交的工单 | ✅                | ✅                   |
| 查看其他员工的工单 | ❌                | ✅                   |
| 查看全部工单       | ❌                | ✅                   |
| 修改工单内容       | ❌                | ❌                   |
| 撤销工单           | ❌                | ❌                   |

### 系统信息边界

不同信息处理原则如下：

| 信息类型     | 示例                 | 处理原则               |
| ------------ | -------------------- | ---------------------- |
| 原始业务信息 | 员工反馈原文         | 完整持久化，不擅自修改 |
| 派生信息     | 分类结果、分类依据   | 可以重新分类、人工纠正 |
| 系统管理信息 | 状态、提交人、操作人 | 系统或授权人员维护     |

不同主体处理信息：

1. 员工只能访问自己工单，技术支持人员暂时访问所有工单，后续可能职责划分。
2. 调用LLM分类时，仅提供分类所需必要内容，不传递用户认证信息及业务数据



## 系统设计

### 基本流程

IssueFlow 以工单为核心，实现从问题提交、智能分类到处理完成的完整业务闭环。员工提交工单后，系统进行输入校验与重复编号检查，保存原始内容，并通过规则优先、LLM 辅助的混合分类机制自动识别问题类型。技术支持人员查看工单并核查分类及信息完整性，必要时人工修正分类或要求员工补充信息；随后处理实际问题，更新工单状态并记录处理结果。员工可随时查看自己的工单进度与处理结果，系统保留关键操作历史，确保处理过程可追溯。工单完成后进入只读状态，不允许再次修改或重新打开。基本流程如下：

### 智能分类机制

这边主要识别4大类别，如果都识别不出来则标为待确认。其主要四大类别如下：

| 类别     | 高确定性表达                                       | 示例                       |
| -------- | -------------------------------------------------- | -------------------------- |
| 系统故障 | 登录失败、页面卡死、点击无响应、导出失败、系统卡顿 | 系统登录页面一直转圈       |
| 权限申请 | 申请权限、开通权限、增加访问权限、授权访问         | 帮我申请项目资料的查看权限 |
| 功能建议 | 希望新增、建议增加、能否优化、希望支持             | 希望查询页面保存筛选条件   |
| 使用咨询 | 如何操作、怎么使用、在哪里设置、如何重置           | 请问怎么重置登录密码       |

然后其采用的分类策略是：**高精度规则匹配 → LLM 语义分类 → 异常降级 → 技术支持人工复核**

1. 首先通过预设的高精度规则识别意图明确的工单，减少模型调用成本；
2. 如果规则无法确定，则调用 LLM 进行语义分类，并对输出格式、类别及原文证据进行校验；
3. 若模型不可用、调用超时或输出不合法，则降级为“待确认”，确保工单正常登记。
4. 最后由技术支持人员对分类错误或待确认的工单进行人工复核，必要时要求员工补充信息，并记录分类修正历史，保证分类结果的可靠性与可追溯性。

### 业务异常与边界处理

### 1. 输入校验与幂等提交

针对空白反馈、非法参数及网络重试导致的重复提交问题，系统采用 **Pydantic 参数校验 + PostgreSQL 唯一约束 + 幂等处理** 的多层保障机制。

在接口层，通过 Pydantic 的 `field_validator` 校验反馈内容，使用 `strip()` 判断是否为空白，并限制内容长度。校验仅用于判断合法性，不覆盖员工提交的原始文本。对于非法输入，返回 HTTP 422，且不执行数据库写入与智能分类。

针对相同 `request_id` 的重复提交，在数据库层建立 `UNIQUE` 唯一约束，并采用 PostgreSQL 的 `INSERT ... ON CONFLICT DO NOTHING RETURNING id` 处理并发插入，避免传统“先查询、后插入”产生的竞态条件。

- 首次提交：创建工单，并返回 HTTP 201。
- 相同编号、提交人及原文重复提交：返回已有工单，不重复创建，也不重复调用分类服务。
- 相同编号但提交人或原文不同：返回 HTTP 409，拒绝覆盖原有数据。
- 两个请求并发提交相同编号：由数据库唯一约束保证最多只有一个插入成功。

幂等判断以首次提交的 `original_text` 为依据，而不是后续可能修改的 `current_text`，确保信息补充不会破坏原始请求的幂等语义。

### 2. 数据库事务与并发控制

针对多名技术支持同时操作同一工单可能产生的数据覆盖问题，系统采用 **PostgreSQL 事务 + 乐观锁（Optimistic Locking）+ 条件更新** 的方案。

在 `tickets` 表中设置 `version` 字段，客户端修改状态时携带读取工单时的版本号。后端通过 `UPDATE ... WHERE id = ? AND version = ? AND status = ?` 执行条件更新，成功后将版本号加一。

例如，技术支持 A 和 B 同时读取版本 V1，A 先将工单更新为“处理中”，版本变为 V2；B 再以 V1 提交修改时，条件更新无法匹配，系统返回 HTTP 409，提示重新获取最新数据，避免静默覆盖。

对于涉及多张表的操作，统一使用数据库事务保证原子性：

- 状态变更：更新 `tickets` 并写入 `ticket_events`。
- 内容修改：更新 `tickets.current_text` 并写入 `ticket_revisions`。
- 信息补充：更新当前内容、关闭补充请求标识并记录修改历史。

上述操作任意一步执行失败，则整个事务回滚，防止出现工单已更新但操作历史缺失的情况。

考虑到当前系统并发规模较小，优先采用数据库原生机制，不引入 Redis 分布式锁或额外的分布式事务框架。

### 3. 智能分类异常降级与结果一致性

针对 LLM 调用超时、模型输出不稳定以及分类结果覆盖等问题，系统采用 **规则优先 + 结构化输出校验 + 异常降级 + 条件回写** 的可靠性设计。

工单首先经过高确定性规则分类，规则无法判断时才调用 DeepSeek API，模型调用超时预算设置为 2 秒。LLM 输出使用 Pydantic 校验，要求类别属于五种预定义类型，同时验证引用的证据是否真实存在于工单内容中。

当 API 未配置、网络异常、请求超时、输出格式不合法或证据校验失败时，系统将类别降级为 `uncertain`（待确认），并记录 `classification_source = fallback`。工单登记与外部模型调用解耦，确保分类服务异常不会造成工单丢失。

针对异步返回的旧分类结果，写入数据库前检查当前内容快照、分类来源及工单状态，仅允许仍处于待分类状态、内容未发生变化且尚未完成的工单接受自动分类结果。

例如，技术支持已经人工将工单修正为“系统故障”，但之前的 LLM 请求随后返回“权限申请”，后端应拒绝该过期结果，保留人工修正结论。

若服务在工单创建后、分类完成前发生异常退出，数据库中仍保留待分类工单，并通过恢复检查将长期未完成的分类任务降级为待确认，交由技术支持处理。

### 4. 身份认证与数据权限隔离

针对企业内部反馈可能包含敏感信息，以及用户通过直接调用 API 绕过页面权限的问题，系统采用 **JWT 身份认证 + RBAC 角色权限 + 数据归属校验** 的访问控制方式。

登录后由后端识别用户身份，区分 `employee` 和 `support` 两类角色。所有业务接口均执行后端权限检查，不能仅依靠前端隐藏操作按钮。

- 普通员工：只能查询自己提交的工单及相关历史。
- 技术支持：可以查询全部工单，并在业务规则允许的范围内更新分类和状态。
- 工单提交者由当前认证身份确定，不能由前端任意指定 `submitter_id`。
- 员工尝试访问其他人的工单时，拒绝访问，并避免泄露目标工单的原文和提交人信息。

数据隔离直接在数据库查询条件中实现，例如员工查询使用 `WHERE submitter_id = current_user.id`，而不是先读取全部工单再由前端过滤。

对于写入接口，除了角色权限，还要进一步验证工单归属和当前业务状态，实现基于角色、资源及状态的联合授权控制。

### 关键技术决策

### 1. 模块化单体架构 vs 微服务架构

**方案选择：** 采用 Next.js + FastAPI 前后端分离架构，后端按照认证授权、工单管理、智能分类和操作审计划分业务模块，使用 PostgreSQL 统一持久化。

**选型依据：** 当前系统面向约 100 名员工和 5 名技术支持人员，日均反馈量约 20～100 条，业务主要集中于工单登记、分类和状态流转。各模块之间存在较强的数据一致性要求，例如工单状态更新必须同时保存操作历史。模块化单体可以直接使用本地业务调用和数据库事务完成跨模块协作，避免引入微服务通信、分布式事务和服务治理成本。

**技术取舍：** 相比微服务，模块化单体无法独立部署或扩缩容单个业务模块，但能够显著降低当前项目的开发、测试与运维复杂度。后续若智能分类调用量明显增加，可优先将分类任务独立为异步 Worker，而不是立即拆分整个后端。

### 2. 规则与 LLM 混合分类 vs 纯 LLM 分类

**方案选择：** 采用高精度规则匹配与 DeepSeek LLM 语义分类相结合的策略，规则优先，无法确定类别时再调用 LLM，并保留技术支持人工修正机制。

**选型依据：** IssueFlow 仅需要识别系统故障、权限申请、功能建议、使用咨询和待确认五类工单。对于“申请系统访问权限”“建议增加导出功能”等明确表述，可以通过高精度规则快速分类，无需每次请求都调用模型；对于表达模糊或上下文复杂的反馈，则利用 LLM 的语义理解能力补充识别。

**技术取舍：** 纯规则方案成本低、结果稳定，但难以覆盖多样化的自然语言表达；纯 LLM 方案规则维护成本低，但引入额外的 API 费用、网络延迟及输出不确定性。混合方案牺牲了部分实现简洁性，需要维护规则与模型提示词，但能够在分类覆盖率、成本和可靠性之间取得平衡。规则仅匹配高确定性场景，不强行追求覆盖所有输入。

### 3. 工单先落库 vs 等待 LLM 分类后入库

**方案选择：** 将工单登记与智能分类拆分为两个独立的持久化阶段。首先保存原始内容并创建待处理工单，数据库提交成功后再执行分类，分类完成后通过独立事务回写结果。

**选型依据：** 工单登记是核心业务，LLM 分类属于辅助能力。若将模型调用放在数据库事务内部，会延长事务持续时间；若必须等待分类成功才能保存工单，则外部 API 超时或不可用可能导致用户反馈丢失。因此系统优先保证工单可靠登记，再尝试完成自动分类。

**技术取舍：** 该方案降低了对第三方模型服务的依赖，但引入了短暂的待分类状态，以及分类任务执行中断后的恢复问题。当前版本不引入 Redis、Celery 或消息队列，而是通过分类状态标记与超时恢复检查处理异常。后续若分类任务量、耗时或可靠性要求明显提高，再考虑使用持久化任务队列和独立 Worker。

### 4. PostgreSQL 乐观锁 vs 悲观锁和分布式锁

**方案选择：** 采用 PostgreSQL 事务、唯一约束及基于 `version` 字段的乐观锁实现工单数据一致性。

**选型依据：** 工单更新主要发生在技术支持人员操作时，写入频率较低，但可能出现多人同时处理同一工单的情况。通过 `UPDATE ... WHERE version = expected_version` 实现条件更新，仅允许基于最新版本的请求修改成功。状态更新、处理结果写入与操作历史记录则在同一数据库事务中提交。

**技术取舍：** 相比数据库行级悲观锁或 Redis 分布式锁，乐观锁不需要在用户操作期间长期持有锁，更适合当前低冲突场景。但发生冲突时需要拒绝旧版本请求，由客户端重新获取最新数据，而不是自动覆盖其他人的操作。若未来出现高频竞争同一资源的业务，再针对具体操作评估行级锁或串行化处理。

### 5. 原文不可变与事件留痕 vs 直接覆盖修改

**方案选择：** 工单表同时保存不可变的 `original_text` 和可受控更新的 `current_text`，通过 `ticket_revisions` 记录正文修改，通过 `ticket_events` 记录分类修正、状态变更、补充请求等关键业务事件。

**选型依据：** 工单可能经过多次信息补充或分类修正。如果直接覆盖原始内容，将难以判断员工最初反馈了什么、技术支持何时修改了分类，也不利于后续排查处理争议。因此系统采用原文保留、当前内容更新和独立历史记录相结合的方式，并通过事务保证数据与历史的一致性。

**技术取舍：** 该方案需要维护额外的数据表，增加写入次数及部分查询复杂度，但能够提供明确的业务追溯能力。相比完整事件溯源（Event Sourcing）架构，当前方案直接在 `tickets` 表保存最新状态，事件表仅负责审计，不通过重放事件恢复业务状态，避免为小规模系统引入过度复杂的事件建模与投影机制。





#### 存在风险和缺口

## **工单处理责任不明确与积压风险**

**现有缺口：** 当前采用技术支持共享工单池，不引入工单指派或接单机制。这种方案适合小规模团队，但正式运行时，可能出现无人主动处理、多个技术支持重复处理、工单长时间停留在待处理状态等问题。

**改进方案：** 增加工单负责人、处理优先级和 SLA 管理机制。例如，为不同优先级配置首次响应和处理时限，并根据 `created_at`、`status` 和最后处理时间识别超时工单。对于长期无人处理或即将超时的工单，发送站内或邮件通知。技术支持可通过原子条件更新认领工单，避免多人重复接单。



## **5. 缺乏可观测性与故障告警**

**现有缺口：** 当前即使具备异常捕获和数据库操作历史，也难以系统性判断服务是否健康。例如，LLM 超时比例突然升高、数据库连接池耗尽、接口错误率增加或者待处理工单持续积压，如果没有监控，往往只能等用户反馈后才能发现。

**改进方案：** 建立日志、指标和告警机制。通过结构化日志记录 `request_id`、请求追踪 ID、接口耗时和异常类型；使用 Prometheus + Grafana 等工具监控 HTTP 5xx 错误率、P95 接口延迟、数据库连接使用率、LLM 调用耗时、分类降级率以及待处理工单数量。对服务不可用、错误率突增和工单积压设置告警阈值。



### 系统扩展与演进设计

当前系统面向约 100 名员工和 5 名技术支持人员，采用 FastAPI + PostgreSQL 的模块化单体架构。考虑到现阶段业务规模较小，暂不引入微服务、分布式缓存等复杂技术，后续根据实际使用情况逐步扩展。

#### 1. 用户量增长

当用户规模扩大、并发请求明显增加时，首先通过压力测试定位性能瓶颈，优化数据库连接池及高频接口。若单实例无法满足需求，可通过 Nginx 负载均衡部署多个 FastAPI 实例。同时，将 LLM 分类任务交由独立 Worker 处理，避免模型调用占用 Web 服务资源。

#### 2. 数据量增长

随着工单及操作历史不断积累，优先通过 PostgreSQL 复合索引、服务端分页和慢查询分析优化性能。例如，为 `tickets(submitter_id, created_at)` 建立索引，提高员工历史工单查询效率；为 `tickets(status, created_at)` 建立索引，提高技术支持筛选待处理工单的效率。当历史数据规模明显影响查询性能时，再考虑数据归档或表分区，暂不进行分库分表。

#### 3. 使用角色变化

当前通过 `users.role` 区分员工和技术支持人员，权限逻辑相对简单。如果后续增加管理员、部门主管等角色，可将固定角色扩展为 `roles`、`permissions`、`user_roles` 和 `role_permissions` 等关联表，实现动态 RBAC。同时引入部门级数据权限，限制不同部门之间的工单访问范围。若技术支持团队扩大，还可增加工单认领与负责人机制，解决共享工单池中责任不明确的问题。

#### 4. 基础设施演进

基础设施的引入以实际瓶颈为依据，而非提前堆叠技术组件。若数据库高频查询成为主要瓶颈，且索引优化后仍无法满足性能要求，可引入 **Redis** 缓存工单统计等读多写少的数据；若 LLM 分类任务持续积压、数据库任务队列难以满足吞吐需求，可引入 **RabbitMQ** 实现任务解耦与可靠消费；若不同业务模块在部署频率、资源需求或团队协作上出现明显差异，再考虑将分类服务等模块拆分为**微服务**。每次架构升级前通过压测和监控确认问题，并评估新增组件带来的部署、维护和数据一致性成本。

### 优先改进的三项内容

如果在当前版本基础上只进行三项改进，我会优先考虑**工单分配与超时管理、数据备份与恢复、智能分类任务可靠性**，重点解决实际业务运行中可能出现的问题。

#### 1. 完善工单分配与超时管理

当前系统采用技术支持共享工单池的方式，没有明确的工单负责人，可能出现多个技术支持重复处理同一工单，或者工单长时间无人处理的情况。

计划在 `tickets` 表中增加 `assignee_id` 和 `priority` 字段，支持技术支持主动认领工单，并通过数据库条件更新避免重复认领。同时引入简单的 SLA 机制，根据工单优先级设置处理时限，对即将超时或长期未处理的工单进行提醒。

**优先原因：** 当前系统已经实现了从工单提交到处理完成的基本流程，但缺少明确的责任分配。相比继续增加功能，首先需要保证每条工单都有人负责，并能及时得到处理。

#### 2. 完善数据库备份与恢复机制

当前系统使用 PostgreSQL 存储工单及操作历史，但数据库事务只能保证操作一致性，无法应对服务器故障、磁盘损坏等问题。计划增加定期自动备份、异地备份和恢复演练，并根据实际业务要求考虑 WAL 归档与时间点恢复（PITR）。

**优先原因：** 工单数据要求至少保留三年，包含原始反馈、修改记录和处理结果。一旦丢失，不仅影响业务使用，也会破坏操作记录的可追溯性。

#### 3. 提高智能分类任务的可靠性

当前采用工单先落库、再调用 LLM 的方案，能够避免分类失败导致工单丢失，但服务异常退出时仍可能留下未完成的分类任务。

计划引入 PostgreSQL 持久化任务队列和独立 Worker，增加任务超时检查、有限重试和失败降级，并通过条件更新防止过期结果覆盖人工分类。

**优先原因：** 智能分类是系统的核心功能之一，需要保证模型超时、服务重启等情况下，工单最终仍能得到明确的分类结果，而不是长期停留在待分类状态。

## API 错误码与校验顺序

本文覆盖应用已定义的业务错误。响应格式为 `{"code":"错误码","message":"说明"}`；客户端根据 code 和 HTTP 状态处理，不依赖 message 的具体措辞。

| HTTP | code | 触发场景 | 客户端处理 |
| --- | --- | --- | --- |
| 401 | `UNAUTHORIZED` | 缺少/过期/无效会话，或账号禁用 | 重新登录 |
| 401 | `INVALID_CREDENTIALS` | 登录账号或密码错误 | 检查账号密码，不泄露账号是否存在 |
| 403 | `FORBIDDEN` | 角色不允许操作，或可见工单不是当前提交者而试图补充 | 停止重试该操作 |
| 403 | `INVALID_ORIGIN` | 写请求 Origin 不在允许列表 | 从配置的同源工作台访问 |
| 403 | `CSRF_FAILED` | 缺少 CSRF Cookie/Header、二者不一致或不匹配会话 | 刷新安全凭证，必要时重新登录 |
| 404 | `TICKET_NOT_FOUND` | 工单不存在，或当前用户不可见 | 不区分不存在与他人记录 |
| 409 | `REQUEST_ID_CONFLICT` | 同编号但提交者或首次原文不同 | 使用新编号；不得覆盖既有记录 |
| 409 | `TICKET_VERSION_CONFLICT` | 期望版本已过期，或未命中更新原子条件 | 刷新详情，确认后再操作 |
| 409 | `TICKET_COMPLETED` | 对已完成工单执行写操作 | 只读，不重开 |
| 409 | `INVALID_STATUS_TRANSITION` | 目标状态不符合状态机 | 使用允许的状态转换 |
| 409 | `CLASSIFICATION_PENDING` | 分类尚未结束时试图完成工单 | 等待分类/恢复，或实际修正为其他分类 |
| 409 | `CLARIFICATION_ALREADY_REQUESTED` | 已有开放补充请求，再次发起 | 等待本轮回应 |
| 409 | `EDIT_NOT_ALLOWED` | 没有开放补充请求时修改正文 | 等待技术支持发起请求 |
| 409 | `CONTENT_UNCHANGED` | 补充正文与当前正文完全一致 | 提交实际补充的合法内容 |
| 413 | `REQUEST_TOO_LARGE` | 请求体超过 32768 字节，包括流式正文 | 缩小请求体 |
| 422 | `INVALID_CONTENT` | 正文不是字符串、仅含空白或缺少必需正文 | 提供非空白字符串 |
| 422 | `CONTENT_TOO_LONG` | 正文超过 5000 Unicode 字符 | 缩短正文 |
| 422 | `INVALID_REQUEST_ID` | 创建编号缺失或不符合字母、数字、下划线、连字符，长度 1–64 | 修正编号 |
| 422 | `INVALID_INPUT` | 其他结构校验失败：额外字段、非法枚举、空原因、分页越界等 | 修正请求；page 为 1–10000，page_size 为 1–100 |
| 429 | `LOGIN_RATE_LIMITED` | 同一来源和用户名在 60 秒内达到 10 次登录尝试 | 等待限速窗口后重试 |
| 503 | `DATABASE_UNAVAILABLE` | 数据库错误，或插入冲突后无法读取对应记录 | 稍后重试；创建重试保留相同编号及原文 |

### 权限优先级

对于已认证、通过 CSRF 且请求结构合法的调用，各业务端点明确采用以下顺序：

| 端点 | 顺序 | 员工对他人工单的结果 |
| --- | --- | --- |
| 详情、历史查询 | 先按角色/归属限定可见记录 | 404 |
| 修改正文 | 先按归属限定可见记录，再校验“提交者本人”、终态、版本、补充授权 | 404，隐藏记录存在性 |
| 修改分类、状态、发起补充 | 先检查 support 角色，再读取可见记录并检查业务前提 | 403，即使编号不存在也不泄露存在性 |

技术支持能看全部工单，但不能代替他人补充正文，因此对他人正文的写请求返回 403。这些不同的优先级是明确的隐私策略，不代表缺少角色校验。

### 幂等与无操作

相同编号、提交者和首次原文的创建重试返回 200，不是错误。版本有效、未完成且目标状态相同时也返回 200，不增加版本或事件。

人工分类接口中，如果类别值没有变化，则返回原记录，不将来源从 rule/llm/fallback/pending 改为 manual，不增加版本，也不产生 `category_corrected`。重复请求仍须通过角色、可见性、终态和版本检查。只有类别实际改变才更新来源为 manual 并写纠正事件。

分类调用失败并不等于提交失败：工单创建返回成功，分类为 `uncertain/fallback`，原因记入事件，不作为 HTTP 错误返回。
